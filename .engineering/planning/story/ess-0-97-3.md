## Why

ESS 0.97.3 was released on 2026-11-22 (<https://github.com/beyond10x/ess/releases/tag/0.97.3>;
0.97.2 was tagged and never released). The operator's order of that day: every repository that
pins ESS moves to 0.97.3. surf pins 0.96.0.

What the release changes, as its notes say:

- Synthesis is faster: its cost grew with the cube of guarded outcomes; each stored row is now
  bound once; witness search and caller readings no longer repeat.
- Breaking (a): `--component <name>` on `synthesize`, `specify validate` and `mutate --emit`
  reports only that component's operations, with new `scope:` and `unrealised:` lines. surf's
  tasks pass no `--component` (`git grep -e --component -- Taskfile.yml taskfiles` prints
  nothing at `896c64d`).
- Breaking (b): read-grant scenarios no longer copy other views' reads, so a synthesized suite
  that holds such scenarios changes.

## Change

Every place that names the ESS release surf builds on names 0.97.3:

- `spec/ess-inputs.yaml`: `requires: ess 0.97.3`.
- `.github/workflows/check.yml`: `ESS_VERSION: "0.97.3"`.
- `conformance/Cargo.toml`: the three git dependencies on `https://github.com/beyond10x/ess`
  at tag `0.97.3`; `conformance/Cargo.lock` follows, and the allow-list of the lock check
  follows where a third-party package of the runner changed.
- `generated/rust/`: regenerated with 0.97.3 and committed; hand-written code that calls it
  is changed where the generated interface changed.
- The gate's numbers that the suite gives (`REFUSALS_MAX` in `Taskfile.yml`, the scenario
  counts named in `AGENTS.md`, the badge `docs/badges/spec.svg` and its line in `README.md`).
- `AGENTS.md` and `README.md`: the sentences that state the release as the current one
  ("the pin `requires: ess 0.96.0`", "`ESS_TOOLCHAIN=0.96.0`", "The forge's workflow installs
  0.96.0", "you need `ess` 0.96.0"). A sentence that records a measurement made with 0.96.0
  keeps its release and its date.

Not changed: planning artifacts and evidence records that name 0.96.0 as the release a
measurement was made with.

## Acceptance

When the story is implemented:

1. `git grep -n '0\.96\.0' -- spec .github conformance/Cargo.toml Taskfile.yml taskfiles`
   prints nothing.
2. `ESS_TOOLCHAIN=0.97.3 slot task suite` and `slot task conform` (the interpreter run) exit 0;
   the report names for the suite: scenarios before and after, refusals before and after, and
   each scenario that 0.97.3 no longer synthesizes or newly synthesizes, by name.
3. No scenario that passed on 0.96.0 and still exists fails on 0.97.3, against the interpreter
   and against the Rust system (`conform-rust`); the two runs' totals agree (`conform-totals`).
4. `generated/rust/` equals a fresh generation with 0.97.3 (the gate's own comparison).
5. The lock check passes for `conformance/Cargo.lock`.
6. The time of `ess verify conform synthesize` for surf's spec is measured with 0.96.0 and
   with 0.97.3 on the same commit of `spec/` and both times are in the report.
7. The gate (`slot --timeout 25m task check-runner`, run once by the coordinator) is green,
   its test step within 120 s.

A defect of ESS 0.97.3 that surf cannot work around inside this story (a scenario lost
without a reason in the release notes, a generated file that does not compile, a wrong
verdict) stops the story: the unit reports the input, the command and the output, and the
coordinator sends it to the ESS session.

## Bounds for every command of this story

- Every build and test runs through the build pool: `cargo` is a shim that takes a slot;
  other commands that compile or test get the `slot` prefix.
- A job in the pool ends after 10 minutes unless it names its time (`slot --timeout <n>m`,
  `SLOT_TIMEOUT=<n>m cargo …`), at most 30 minutes. A killed command is not started again
  unchanged.
- A script that measures or waits starts without the `slot` prefix.
- No test runs over 60 s; the test step of the gate ends within 120 s.
- No new Python. No network request, model call or real API call in a test.
